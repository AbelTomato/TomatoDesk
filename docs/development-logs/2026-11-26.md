## ##10:12:00-three-domain-model

## ##21:20:00-email-s0-id-fix

- 背景：用户跑 163 真实账号探针，报 `ID 命令失败（不中断）：Unable to parse status response`，紧接着 `client.rs:1369` 的 tag 断言失败（`left: [97,51]` = `a3`，`right: [97,52]` = `a4`）。
- 根因：`imap-proto 0.10.2` 不认识 RFC 2971 的 `* ID (...)` 未标记响应，`Connection::read_response_onto` 解析返回 `ParseError::Invalid`（`error.rs:155` 的文案），且此前读到的 `a3 OK` 未被消费；下一条命令（`EXAMINE`）发送 `a4` 后读到残留的 `a3 OK`，`assert_eq!(tag, match_tag)` panic。所以上一轮的 `EXAMINE` 根本没执行，报错现场与真因完全错位。
- 另一个隐患：`imap::connect` 不能设置超时，后台轮询遇到半开连接会永久挂住。
- 定稿改法：不再用 `imap::connect` + `run_command_and_read_response("ID …")`，改为 `TcpStream::connect_timeout(8s)` → 读写超时 15s → native_tls 握手 → 逐字节自读问候（不能套 `BufReader`，会预读走后续响应）→ **登录前**发 `a0 ID (...)` 并自读到 `a0` 状态行 → `imap::Client::new(stream)` 接管（tag 从 `a1` 起，不撞号）→ `login`。问候已被自己消费，不能再调 `read_greeting()`（它 `assert!`），`login` 不检查该标志。
- 探针改造：`tests/email_probe.rs` 重写为双场景 —— 场景 B（先发 ID 再登录）与场景 A（不发 ID 直接 EXAMINE），一次运行即可判定 163 是否真的必需 `ID`；`inspect()` 抽出登录后到取首封信的公共流程。
- 实测（无账号部分）：`imap.163.com:993` 问候 `* OK Coremail System IMap Server Ready(...)`，登录前 `ID` 被接受，返回 `* ID ("name" "Coremail Imap" "vendor" "Mailtech" ...)` + `a0 OK ID completed`。说明 ID 可以放在认证前，彻底绕开 `imap-proto` 的解析缺陷。
- 门禁：`cargo fmt --check`、`clippy --all-targets -- -D warnings`、`cargo test --locked`（49 + 1 编码用例通过，探针 1 ignored）均通过。
- 待办：用户带账号跑一次双场景探针，确认 `EXAMINE` 与 `BODY.PEEK[HEADER]` 取信；随后进 S1。
