## ##10:07:00-inbox-capture-flow

- 讨论：「收件箱 → 随手记」是否必要。
- 结论：不是结构必需，而是可选的保留期契约切换口；只在「收件箱短期清理 + 搜索仅覆盖随手记」的前提下需要。
- 约束：手动、单向快照、提取资源而非镜像消息、不做双向关联；实现放命令层或前端，避免 inbox 领域依赖 capture。
- 调整：计划中该能力从阶段二移出，改为阶段三可选增强；核心拆分不依赖它。

## ##10:12:00-three-domain-model

- 讨论：用户明确「随手记是持久化个人资产，收件箱是待办与事务处理」，GitHub 通知可忽略或丢到待办。
- 结论：模型从两域调整为三域——收件箱负责判断、待办负责执行、随手记负责沉淀；待办独立建表，不塞回 captures。
- 数据模型：新增 `tasks`；`inbox_messages` 用 `read_at` / `triaged_at` / `triage_outcome` / `triage_ref_id` 表达判断结果，忽略为软删除，转待办用事务并受唯一索引约束。
- 计划：重写 `docs/execution-plans/2026-11-26-capture-inbox-split.md`，迁移拆为 0005 captures、0006 tasks、0007 inbox，阶段调整为随手记 → 待办 → 收件箱 → GitHub → 邮件。
- 状态：方案待评审，尚未改代码。
