## ##09:42:00-email-s3-sync

- 目标：阶段五 S3，IMAP 取信与多账户轮询，把「能连一次」变成「无人值守持续收信」。
- 决策（评审确认）：首次窗口取最新 100 封（更早的不再补拉）；本轮实现 STARTTLS；引入 `MailFetcher` 以便离线测编排；取信策略原定 partial fetch。
- `infrastructure/email/client.rs`（新增）：`MailCursor`（`uidValidity`/`lastUid`，坏 JSON 与 `lastUid=0` 视为无游标）、`FetchOutcome`、`probe`、`fetch_new(account, password, cursor, deadline)`。建连 = `connect_timeout(8s)` + 15s 读写超时 → implicit TLS 或 `s0 STARTTLS` 升级 → 自读问候 → 登录前发 `a0 ID` → `Client::new` 接管（tag 从 `a1` 起，三者不撞号）。认证先 `LOGIN`，仅当错误为 `BAD` 时回退 `AUTHENTICATE PLAIN`；`NO`（凭证被拒 / `Unsafe Login`）直接按认证失败处理。取信 `EXAMINE` 只读 → 增量 `UID <last>:*` 再按 `uid > last` 过滤 → 首次 `SINCE <今天-14d>` → 排序选批 → 每 20 封 `UID FETCH (UID RFC822.SIZE INTERNALDATE BODY.PEEK[])` → 回填 `server` 元数据、`Date` 缺失用 `INTERNALDATE`。
- `application/inbox/email.rs`：`MailFetcher` trait + `ImapFetcher`；`sync_account`（先入库后写游标，失败写 `last_error` 且游标不动）；`sync_all`（串行、5 分钟整轮预算、60 秒单账户、`spawn_blocking`、每账户发一次事件，失败发 `null`，无账户/无凭据/退避中不发事件）；`Backoff`（进程内、按 source id、60 分钟）；`start_poller`（10 分钟、首轮立即、`MissedTickBehavior::Delay`）。删掉 `to_new_message` 的 `allow(dead_code)`。
- `lib.rs`：`setup` 注册 `application::inbox::email::start_poller`，与 GitHub 轮询、回写 worker 并列。
- 实测修正（重要）：`BODY.PEEK[]<0.262144>` 会让 `imap-proto 0.10.2` 解析失败——`msg_att_body_section` 的序号只认 `<n>`，收到 `<0.262144>` 返回 `Err(Alt)`；`<0>` 才能解析。临时加 `imap-proto` dev-dep 跑 `parse_response` 确认后已还原依赖。因此放弃 partial fetch，改为分批整封取（每批 20 封）约束峰值内存，方案 6.3/6.4 已同步更正。
- 其它实测口径：`ZeroCopyResult<T>` 就是 `Result<ZeroCopy<T>, imap::Error>`（不是元组错误）；`Fetch::body()` 忽略 `index`，`BODY[]<0>` 仍可取到数据；`Session::examine` 返回 `imap::types::Mailbox`，`uid_validity`/`uid_next` 都是 `Option`；`uid_search` 的查询串不做校验，`SINCE` 日期必须代码生成；`Client` 未认证态没有 `capabilities()`，所以 PLAIN 回退只能看错误类型。
- 验证：`cargo fmt --check`、`clippy --all-targets -- -D warnings`、`cargo test --locked` 96 通过（新增 19 个：客户端 8 + 编排 10 + 1 日期格式），探针 1 ignored，全部不触网。
- 状态：S3 完成并提交。自动化只覆盖到假取信器，真实账号的端到端同步仍需手工验证。
- 下一步：S4 命令层（`list/test/save/delete_email_account` + DTO 校验 + 错误映射 + 注册），届时一并确认「删除账户清 `config_json` 用空串还是改 `Option`」——现在仓储按 `String` 读，写成 NULL 会 `InvalidColumnType`。

## ##10:05:00-email-s4-commands

- 目标：阶段五 S4，四个 IPC 命令（list / test / save / delete）+ DTO 校验 + 错误映射 + 注册，让 S5 只写界面。
- `commands/email.rs`（新增）：`*_in` 版本便于离线测试，`#[tauri::command]` 只做入参解析、`spawn_blocking` 与错误透传。保存顺序「校验 → 派生 id → 上限检查 → 试连 → 写凭据 → upsert」，试连失败不落库、不覆盖旧凭据。
- 两个替换点：`MailProber`（`ImapProber`，放 `application::inbox::email`，与 `MailFetcher` 同层）与 `EmailCredentials`（`KeyringCredentials`，命令层私有）。没有它们，命令测试会真的连邮箱并写 Windows 凭据库。
- 首轮同步：`sync_all` 抽出 `sync_selected(only)`，新增 `sync_account_soon(database, app, source_id)`，保存成功后立即同步该账户，用独立退避表——用户刚改完配置，上次失败不该拦住这次重试。
- `commands/dto.rs`：`EmailAccountInput` → `EmailAccountForm`。地址必须含 `@` 且无空白；主机拒绝 `://`、`:`、`/`；端口缺省按 tls 补 993/143、`0` 拒绝；`mailbox` 拒绝控制字符；`password` ≤512 只去首尾空白。
- 三处决策：
  1. `password` 改选填（原契约必填）：编辑端口 / 加密方式时留空即沿用已存凭据，否则每次改端口都要用户重找授权码。已同步计划 5.2。
  2. 删除账户把 `config_json` 写成 `{}`：列上是 `NOT NULL DEFAULT '{}' CHECK (json_valid(config_json))`，空串触发 `SQLITE_CONSTRAINT`（被映射成 `conflict`，两个删除用例因此先红），`NULL` 又会让 `list_email` 的 `String` 读取报 `InvalidColumnType`。空对象两处都满足，且 `EmailConfig::parse` 判为未配置。仓储新增 `clear_config`，注释写明原因。
  3. 上限只拦新增：同 id 且 `enabled = 1` 时跳过计数，改端口不会因为满 5 个失败。
- 门禁口径：`scripts/windows-cargo.ps1` 的 `ValidateSet` 补了 `fmt`（原文档里的 `fmt --check` 会被参数校验直接拒绝）；clippy 的位置参数写法会被 PowerShell 把 `--` 绑错，实际用 `-Command clippy -CargoArgs "--all-targets","--","-D","warnings"`，已写进计划 9.4。
- 验证：`cargo test --locked` 105 通过（新增 9 个，全在 `commands/email.rs` 内联），探针 1 ignored；`fmt --check`、`clippy --all-targets -D warnings` 通过，全部不触网。
- 状态：S4 完成并提交，`c6e1931 feat(inbox): manage email accounts over IPC`（8 文件，+751/−6，含包装脚本的 `fmt` 支持）。真实账号的「保存 → 首轮同步」要等 S5 界面接好才能手工验证。
- 下一步：S5 前端（`api.ts` 四个调用 + preview 桩、`SettingsPage` 邮箱账户区块、`InboxPage` 同步时间与空状态、`InboxMessageDetail` 相关区分支、`fixtures.ts` 两个邮箱来源）。
