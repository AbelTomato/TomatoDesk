## ##09:42:00-email-s3-sync

- 目标：阶段五 S3，IMAP 取信与多账户轮询，把「能连一次」变成「无人值守持续收信」。
- 决策（评审确认）：首次窗口取最新 100 封（更早的不再补拉）；本轮实现 STARTTLS；引入 `MailFetcher` 以便离线测编排；取信策略原定 partial fetch。
- `infrastructure/email/client.rs`（新增）：`MailCursor`（`uidValidity`/`lastUid`，坏 JSON 与 `lastUid=0` 视为无游标）、`FetchOutcome`、`probe`、`fetch_new(account, password, cursor, deadline)`。建连 = `connect_timeout(8s)` + 15s 读写超时 → implicit TLS 或 `s0 STARTTLS` 升级 → 自读问候 → 登录前发 `a0 ID` → `Client::new` 接管（tag 从 `a1` 起，三者不撞号）。认证先 `LOGIN`，仅当错误为 `BAD` 时回退 `AUTHENTICATE PLAIN`；`NO`（凭证被拒 / `Unsafe Login`）直接按认证失败处理。取信 `EXAMINE` 只读 → 增量 `UID <last>:*` 再按 `uid > last` 过滤 → 首次 `SINCE <今天-14d>` → 排序选批 → 每 20 封 `UID FETCH (UID RFC822.SIZE INTERNALDATE BODY.PEEK[])` → 回填 `server` 元数据、`Date` 缺失用 `INTERNALDATE`。
- `application/inbox/email.rs`：`MailFetcher` trait + `ImapFetcher`；`sync_account`（先入库后写游标，失败写 `last_error` 且游标不动）；`sync_all`（串行、5 分钟整轮预算、60 秒单账户、`spawn_blocking`、每账户发一次事件，失败发 `null`，无账户/无凭据/退避中不发事件）；`Backoff`（进程内、按 source id、60 分钟）；`start_poller`（10 分钟、首轮立即、`MissedTickBehavior::Delay`）。删掉 `to_new_message` 的 `allow(dead_code)`。
- `lib.rs`：`setup` 注册 `application::inbox::email::start_poller`，与 GitHub 轮询、回写 worker 并列。
- 实测修正（重要）：`BODY.PEEK[]<0.262144>` 会让 `imap-proto 0.10.2` 解析失败——`msg_att_body_section` 的序号只认 `<n>`，收到 `<0.262144>` 返回 `Err(Alt)`；`<0>` 才能解析。临时加 `imap-proto` dev-dep 跑 `parse_response` 确认后已还原依赖。因此放弃 partial fetch，改为分批整封取（每批 20 封）约束峰值内存，方案 6.3/6.4 已同步更正。
- 其它实测口径：`ZeroCopyResult<T>` 就是 `Result<ZeroCopy<T>, imap::Error>`（不是元组错误）；`Fetch::body()` 忽略 `index`，`BODY[]<0>` 仍可取到数据；`Session::examine` 返回 `imap::types::Mailbox`，`uid_validity`/`uid_next` 都是 `Option`；`uid_search` 的查询串不做校验，`SINCE` 日期必须代码生成；`Client` 未认证态没有 `capabilities()`，所以 PLAIN 回退只能看错误类型。
- 验证：`cargo fmt --check`、`clippy --all-targets -- -D warnings`、`cargo test --locked` 96 通过（新增 19 个：客户端 8 + 编排 10 + 1 日期格式），探针 1 ignored，全部不触网。

- 目标：审阅 v0.5.0 使用中暴露的三个问题（界面文案、收件箱一键处理、已判断/未判断命名），给出按优先级排序的改进建议。

- 核心结论：三项是同一问题的三个切面——把建模语言当成了产品语言。优先级与用户列举顺序不同：①A 文案止血（半天，零风险）→ ③ 换模型 + 撤销（1 天）→ ② 批量（依赖③的撤销，否则不可逆操作被放大）。
- 关键证据：`counts.unread` 只统计未处理且未读，而「只看未读」筛选是 `read_at IS NULL`（含已处理），同一词两处口径不同；`dismiss` 写 `triaged_at` 后详情页动作全部消失，无撤销入口（`repositories/inbox_message.rs` 只有 `dismiss`/`to_task`，没有反向操作）。
- 批量可行性：数据层够用（`triaged_at` + partial index + 幂等 WHERE），不需要迁移；真风险是批量已读会向 GitHub 回写队列灌 N 条请求（worker 一分钟一轮逐条 PATCH），需在方案里限定只写本地或合并。
- 状态：文档已写，未改任何代码；`prettier --check` 通过。下一步等评审确认 4.6 的决策点（尤其撤销「已转待办」时待办去留、是否需要跨分页全选）。
