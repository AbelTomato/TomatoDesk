## 1. 基线：现在的实现长什么样

### 1.1 数据

`inbox_messages`（0007）：`read_at` 是标记，`triaged_at + triage_outcome + triage_ref_id` 是处理结果，三条 CHECK 保证「有时间必有结果」。
`tasks`（0006）：`origin_kind = 'inbox'` 且 `origin_id = message.id`，并有 `tasks_inbox_origin_unique` 局部唯一索引。

### 1.2 三个必须先承认的约束

1. **唯一索引决定撤销怎么做**。消息回到待处理而待办仍占着 `origin_id`，第二次「转为待办」会撞唯一索引，被映射成 `conflict`，用户无法理解。所以撤销「已转待办」必须解除关联。
2. **邮件 UID 已经存在库里**，只是藏在 `payload_json`（`application/inbox/email.rs:163` 写入 `"uid"` 与 `"uidValidity"`）。回写 `\Seen` 不需要新取一次信，但需要把它从 JSON 里提出来。
3. **回写队列是 GitHub 专用**。`github.rs:180` 在拿不到 GitHub Token 时整轮跳过，`plan_failure` 只认 `GithubError`。要承载邮件，队列必须按 `action` 分派，失败分类也要按来源分开。

### 1.3 现状里两个具体的错

- `InboxPage.tsx:435`：`{ id: "triaged", label: "已判断", count: counts.all - counts.pending }` —— 用减法凑计数，Tab 里同时装着「已忽略」和「已转为待办」。
- `counts.unread` 只统计「未读且未处理」，而「只看未读」筛选是 `read_at IS NULL`，同一个词两个口径。

## 2. 目标模型

| 状态     | 存储                           | 界面                                  |
| -------- | ------------------------------ | ------------------------------------- |
| 待处理   | `triaged_at IS NULL`           | Tab「待处理」                         |
| 已转待办 | `triage_outcome = 'task'`      | Tab「已转待办」                       |
| 已忽略   | `triage_outcome = 'dismissed'` | Tab「已忽略」                         |
| —        | `read_at` 非空                 | 行首圆点 + 「只看未读」开关，不占 Tab |

Tab 顺序：`待处理 · 已转待办 · 已忽略 · 全部`。四者互斥且穷尽，计数直接从各自条件算出，不再做减法。

## 3. 迁移 0009（一次性，只加不改）

```sql
-- 处理来源：NULL 是人处理的，'rule' 是规则自动处理的。
ALTER TABLE inbox_messages ADD COLUMN triage_by TEXT
    CHECK (triage_by IS NULL OR triage_by = 'rule');

CREATE INDEX inbox_messages_outcome
    ON inbox_messages(triage_outcome, occurred_at DESC, id DESC)

-- 队列从「只有 GitHub 已读」扩成「按动作分派」。
ALTER TABLE inbox_read_back ADD COLUMN action TEXT NOT NULL DEFAULT 'github_read'
    CHECK (action IN ('github_read', 'email_seen'));
ALTER TABLE inbox_read_back ADD COLUMN uid INTEGER;
ALTER TABLE inbox_read_back ADD COLUMN uid_validity INTEGER;

CREATE TABLE inbox_rules (
    id TEXT PRIMARY KEY NOT NULL,
    source_id TEXT REFERENCES inbox_sources(id) ON DELETE CASCADE,
    category TEXT,
    actor_contains TEXT,
    title_contains TEXT,
    action TEXT NOT NULL CHECK (action IN ('read', 'dismiss')),
    enabled INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0, 1)),
    hit_count INTEGER NOT NULL DEFAULT 0 CHECK (hit_count >= 0),
    last_hit_at TEXT,
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    CHECK (source_id IS NOT NULL OR category IS NOT NULL
           OR actor_contains IS NOT NULL OR title_contains NOT NULL)
);

CREATE INDEX inbox_rules_enabled ON inbox_rules(enabled, created_at, id);
```

三点说明：

- **只加列，不改列**。旧版本程序显式列出字段查询，读 v9 库不会报错；万一需要退回 0.5.0，也只是看不到新功能，不会打不开。
- **迁移前自动备份**已有机制（`database.rs:210 backup_database`，落在 `<data>/backup`），S2 落地后第一次启动会生成备份，作为唯一的回滚手段——`ALTER TABLE ADD COLUMN` 在 SQLite 里无法撤销。
- `inbox_rules` 的 CHECK 是「空条件规则会吞掉整个收件箱」的最后一道闸。

       SUM(triaged_at IS NULL),

## 6. S3：选择 + 动作 + 撤销

### 6.1 命令契约

```ts
type InboxAction = "read" | "unread" | "dismiss" | "task";

applyInboxAction({
  action: "dismiss",
  ids: ["m1", "m2"],          // 二选一
  scope?: InboxScope,          // 「选择全部 N 条」
  expectedCount: 2,
}): { action, appliedIds, taskIds, skipped }

undoInboxAction({
  action: "dismiss",
  ids: appliedIds,
  taskIds: [],
}): { action, appliedIds, taskIds, skipped }
```

一次动作只保留最近一次，撤销完全由前端把 `appliedIds` 带回来，**后端不需要 session 或持久化的 undo 表**——这就是「内存态」在接口上的样子。

### 6.2 应用层

`application/inbox/mod.rs` 新增一个 `apply_action(database, action, ids) -> InboxActionResult`，四个动作全部走它：

| 动作      | SQL                                                                              | 撤销            |
| --------- | -------------------------------------------------------------------------------- | --------------- |
| `read`    | `SET read_at = now WHERE id = ? AND read_at IS NULL`                             | `unread`        |
| `unread`  | `SET read_at = NULL WHERE id = ? AND read_at IS NOT NULL`                        | `read`          |
| `dismiss` | `SET triaged_at, triage_outcome='dismissed' WHERE id = ? AND triaged_at IS NULL` | 清三字段        |
| `task`    | 事务内 `INSERT tasks` + `SET triage_outcome='task', triage_ref_id`               | 清三字段 + 解绑 |

- **只统计真正改变的行**（`changed > 0` 才进 `applied_ids`），撤销才不会把用户早就标过已读的消息翻回未读。
- **整批一个事务**：200 条批量忽略要么全成要么全不成，不做「部分成功」。
- 违反约束（例如消息在确认期间已被别的路径处理）只 `skipped += 1`，不报错。

### 6.3 范围选择与守卫

`scope` 模式在后端 `SELECT id ... WHERE <scope>` 解析，上限 2000 条：

- 先 `count`，与 `expectedCount` 比对，不一致返回 `stale` + 实际数字，前端弹「现在是 137 条，仍要处理吗」；
- 再取 id 执行。两次查询在同一事务内，避免中间插入新消息。

保守上限的理由：一次性处理上万条会让主线程卡住、也可能误伤，2000 条足够覆盖真实积压。

### 6.4 撤销「已转待办」＝解绑保留（已确认）

```sql
UPDATE tasks SET origin_id = NULL, updated_at = now
WHERE id IN (...) AND origin_kind = 'inbox';
```

- 待办保留，标题、备注、完成状态都不动，`origin_kind` 仍是 `'inbox'`（列表里仍显示「来自收件箱」，只是没有「查看原消息」入口）。
- `origin_id` 置空后局部唯一索引不再拦路，用户可以再次转换。
- 若待办已被删除（用户在待办页删掉），跳过，不算失败。

新增两个文件，避免 `InboxPage.tsx` 从 705 行涨到 1000+：

2. 操作条：`已选 12 条 · 标为已读 · 标为未读 · 忽略 · 转为待办 · 取消`。忽略不设主按钮样式。

## 7. S4：邮件 `\Seen` 回写

已确认在 v0.6 做，且不做「按账户开关」。

### 7.1 入队

标已读时，`github::enqueue_read_back` 扩成 `enqueue_read_back(database, message, action)`：

```sql
INSERT INTO inbox_read_back(id, message_id, source_id, external_id, action, uid, uid_validity, next_attempt_at)
SELECT ?1, m.id, m.source_id, m.external_id, 'email_seen',
       json_extract(m.payload_json, '$.uid'),
       json_extract(m.payload_json, '$.uidValidity'),
       strftime('%Y-%m-%dT%H:%M:%fZ', 'now')
FROM inbox_messages m
WHERE m.id = ?2 AND json_extract(m.payload_json, '$.uid') IS NOT NULL
ON CONFLICT(source_id, external_id) DO UPDATE SET ...
```

取不到 UID（历史数据、非邮件来源）则不入队，静默跳过。

### 7.2 执行

`infrastructure/email/client.rs` 新增：

```rust
pub fn store_seen(account: &EmailAccount, password: &str, uids: &[u32], deadline: Instant)
    -> Result<(), EmailError>;
```

- 现有 `connect()` 之后走的是 `EXAMINE`（只读），`STORE` 在只读模式下会被服务器拒绝。需要把选箱拆成 `select(stream, read_only: bool)`：取信仍 `EXAMINE`，回写用 `SELECT`。
- 一条命令写多封：`UID STORE 12,15,31 +FLAGS.SILENT (\Seen)`，单批 ≤ 200 个 UID。
- `+FLAGS.SILENT` 避免每封回一个 untagged FETCH。

### 7.3 调度

`process_due` 按 `action` 分派：

- `github_read` → 现有逻辑，不变（无 Token 仍整轮跳过）；
- `email_seen` → 按 `source_id` 分组，每个账户一次连接、一条 STORE。

`uid_validity` 守卫：执行前读该来源的游标，若与行上的 `uid_validity` 不一致，说明服务器重排过 UID，**直接删行丢弃**，宁可少标一封也绝不标错一封。

失败分类按来源分开：认证失败 `block`（等用户改密码），网络错误按现有退避重试，UID 不存在（`NO` / 找不到）直接 `drop`。

### 7.4 影响

- 发布说明里「只读收信，不会改变网页邮箱的已读状态」这句话必须改写，否则就是虚假承诺。
- 设置页「已读回写」区块的文案要覆盖两种来源（GitHub 通知、邮件），并说明邮件是「标为已读时同步」。
- QQ / 163 对 `STORE` 有频率限制：合并成单条命令后，一轮一封连接，风险可接受；连续快速标 100 封会产生 2 条命令。

验收：真实 Gmail 账号标一封已读 → 一分钟内网页端变已读；同时确认标记未读**不会**把它翻回未读（本期只做 `+FLAGS`，不做 `-FLAGS`，需在文案里说清）。

## 8. S5：规则化自动处理

### 8.1 匹配时机

`repositories/inbox_message.rs::ingest` 返回值从 `InboxMessage` 改成 `IngestOutcome { message, created }`（插入前先 `SELECT 1` 判存在）。

规则**只对 `created == true` 的新消息生效**，理由：重新同步的老消息已经被人看过或处理过，再让规则改写结果，会出现「撤销之后又被规则收回去」的循环。

### 8.2 应用

`application/inbox/ingest` 在拿到新消息后：

1. `inbox_rules().enabled()` 取规则（条件为「且」，全空由 CHECK 挡住）；
2. 按 `created_at` 顺序取第一条命中；
3. 调 `apply_action` 同一个实现，额外写 `triage_by = 'rule'`、`hit_count += 1`、`last_hit_at`。
