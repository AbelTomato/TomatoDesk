## 1. 总体判断

三个问题不是三件事，而是同一个问题的三个切面：**把建模语言和实现细节当成了产品语言**。

- 收件箱的核心状态被命名为「判断」。这是设计文档里的 triage，不是用户脑中的词。用户想的是「这条要不要管」。
- 因为「判断」不好懂，界面开始用文案解释模型——「阅读与判断是两件事」「判断结果不会被后续同步覆盖」「读完可以先放着」。文案一旦开始替模型辩护，就说明模型没在界面上自证。
- 因为每条消息都必须单独做一次不可逆的决定，「待判断」很快积压，于是自然产生「能不能一键处理」的诉求。

所以优先级不是用户列出的 ①②③，而是 **①（止血）→ ③（换模型）→ ②（提效率）**。先做批量会把「不可撤销」的代价放大 N 倍，顺序反了会返工两次。

| 顺序 | 工作                  | 性质           | 预估     | 依赖     |
| ---- | --------------------- | -------------- | -------- | -------- |
| P0   | ①A 删除设计与实现说明 | 纯文案，零风险 | 半天内   | 无       |
| P1   | ③ 状态模型 + 撤销     | 前端 + 后端    | 1 天     | 无       |
| P1   | ①B/C 精简与统一文案   | 前端           | 半天     | ③ 的命名 |
| P2   | ②A 选择 + 动作 + 撤销 | 前端 + 后端    | 1–1.5 天 | ③ 的撤销 |
| P3   | ②B 跨分页全选         | 前端 + 后端    | 0.5–1 天 | ②A       |
| P4   | ②C 规则化自动处理     | 后端 + 设置页  | 2–3 天   | ②B       |

## 3. ③ 「已判断 / 待判断」状态模型

### 3.1 现状的五个问题

1. **词不对。** 「判断」是内部建模词，用户在收件箱里做的是「处理 / 不管」，不是「判断」。
2. **桶混了。** 「已判断」同时装「已忽略」和「已转为待办」，Tab 名不携带结果；用户必须逐行读 Badge 才知道发生了什么。而「已判断」计数是 `all - pending` 算出来的，本身不区分结果。
3. **两轴并列。** 已读与已处理是正交的两件事，但头部把「待判断 N · 未读 M」并排显示，像同级计数；`counts.unread` 只统计「未读且未处理」，而「只看未读」筛选用的是 `read_at IS NULL`（含已处理），同一个词在两处口径不同。
4. **不可撤销。** `dismiss` 写入 `triaged_at` 后，详情页所有动作消失，没有撤销入口。误点只能改数据库。这是最伤的一处，也是 ② 的前置障碍。
5. **文案在替模型解释。** 见 2.2，三处说明性文案都指向同一个缺口。

### 3.2 建议模型：一个状态轴 + 一个视觉标记

把「判断」换成「处理」，并把结果直接放进 Tab：

| Tab      | 过滤条件                       | 空态                 |
| -------- | ------------------------------ | -------------------- |
| 待处理   | `triaged_at IS NULL`           | 收件箱已清空         |
| 已转待办 | `triage_outcome = 'task'`      | 还没有转成待办的消息 |
| 已忽略   | `triage_outcome = 'dismissed'` | 还没有忽略的消息     |
| 全部     | 无                             | 收件箱是空的         |

- 已读降级为**视觉标记 + 一个开关**：未读圆点 + 「只看未读」，不再进头部计数。头部只留「待处理 N 条」。
- 若坚持保留未读计数，必须先把 `counts.unread` 改成 `read_at IS NULL`，与筛选口径一致；同时补一个 `WHERE read_at IS NULL` 的 partial index（现有 `inbox_messages_unread` 带 `triaged_at IS NULL`，改口径后命中不了）。
- 列表行 Badge 只在「全部」与「待处理」显示；在「已转待办 / 已忽略」里是冗余信息。
- 导航角标继续显示「待处理」数，语义不变。

四项比三项好，理由是：**「已忽略」是用户回来救错误的地方**，藏在「已处理」里会让人找不到。

### 3.3 撤销（与模型同批交付）

- 撤销不再单独设计：它就是 ② 的动作模型对单条执行后的逆操作，命令统一为 `undo_inbox_action`。
  - `dismissed` → 清空 `triaged_at / triage_outcome / triage_ref_id`，回到待处理，无损。
  - `task` → 清空三个字段，并解绑待办（`tasks.origin_id = NULL`），待办本身保留，详见 5.2。
- 详情页已处理状态改为：`已忽略 · 3 分钟前` + 「撤销」按钮；不再有说明性段落。撤销按钮与批量撤销共用同一套 5 秒内存记录，只是记录里只有一条 id。
- 后端约束不变：`WHERE triaged_at IS NOT NULL` 才允许撤销，重复点击幂等。

| 位置       | 现状                   | 建议                              |
| ---------- | ---------------------- | --------------------------------- |
| Tab        | 待判断 / 已判断 / 全部 | 待处理 / 已转待办 / 已忽略 / 全部 |
| 头部       | 待判断 12 · 未读 3     | 待处理 12 条                      |

## 4. ② 选择 + 动作

### 4.1 结论：不做「一键处理」，做「选择 + 动作」

评审决定把操作抽象掉：**先选一批消息，再对这批消息执行一个动作**。不存在「一键处理收件箱」这个特殊功能，它只是「全选 + 忽略」的一次普通组合。

这个抽象带来三个简化：

- **单条与批量同一条路径。** 详情页的「转为待办」「忽略」就是「选中 1 条 + 执行动作」，不需要两套命令、两套错误处理、两套撤销。
- **动作与范围正交。** 范围是「当前页 12 条」还是「筛选命中的 137 条」，动作是已读、忽略还是转待办，自由组合，不必为每种组合写一个入口。
- **给规则化留了口子。** 规则无非是「系统替你选好一批，再执行同一个动作」，复用同一套事务与撤销。

代价是收件箱多了一个选择态，`InboxPage` 需要拆分。

### 4.2 动作集

| 动作     | 落库                                      | 撤销                       | 备注                               |
| -------- | ----------------------------------------- | -------------------------- | ---------------------------------- |
| 标为已读 | `read_at = now`，GitHub 来源入回写队列    | `read_at = NULL`，删队列行 | 不清列表，只改视觉状态             |
| 标为未读 | `read_at = NULL`，撤销队列行              | `read_at = now`，重新入队  | 与上一条互为逆操作                 |
| 忽略     | `triaged_at = now`，`outcome = dismissed` | 清空三个判断字段           | 移出待处理，不删数据               |
| 转为待办 | 事务内写 `tasks` + 回填 `triage_ref_id`   | 解绑保留待办 + 清判断字段  | 解绑后唯一索引不再拦路，可再次转换 |

四种动作全部实现为 `apply_inbox_action(selection, action)`，单条只是 `ids.length === 1`。不做物理删除，不做「提取为随手记」（后端还没有对应事务）。

### 4.3 选择模型与全选

```ts
type InboxSelection =
  { mode: "ids"; ids: string[] } | { mode: "filter"; filter: InboxFilter; excludedIds: string[] };
```

- `ids`：当前页勾选的条目，前端直接持有。
- `filter`：全选「命中当前筛选的全部消息」，跨分页。前端不持有这些 id，后端在执行时用同一套 SQL 解析，所以「全选 137 条」不需要先把 137 条拉到前端。
- `excludedIds`：给「全选之后又取消勾选几条」留位置，第一版可以不做。

**计数守卫**：操作条上的数字是打开时的快照，执行时可能已被同步改变。命令带 `expectedCount`，解析出的数量不符就不执行，返回 `count_mismatch` 与最新数量，由前端重新确认。避免「确认 123 条、执行 137 条」。

**撤销快照**：执行结果返回 `appliedIds`，只用于撤销，不渲染。撤销只认 id，不重新按筛选取——否则同步又插进来几条，撤销范围和执行范围就对不上了。

### 4.4 交互流程

1. 头部「选择」进入选择态：行首出现复选框，底部浮出操作条。
2. 操作条：`已选 12 条 · 标为已读 · 忽略 · 转为待办 · 取消`。
3. 全选：未加载更多时选中当前页全部；`hasMore` 时操作条追加「选择全部 137 条」，切到 `filter` 模式。
4. 命中数超过 20 时执行前弹一次确认：列出前 5 条标题与总数，按钮写动作与数量，例如「忽略 137 条」，不写「确定」。
5. 执行后就地更新列表与计数，顶部 callout：`已忽略 137 条 · 撤销`。
6. 5 秒后 callout 消失，撤销入口关闭；`Esc` 或点空白退出选择态。

### 4.5 撤销（内存态，5 秒）

前端持有 `{ action, appliedIds, createdTaskIds, at }`，5 秒内可撤销，过期丢弃；不落库、不跨窗口、重启即失效。只保留最近一次，新动作覆盖旧记录。

| 动作     | 撤销做法                                           |
| -------- | -------------------------------------------------- |
| 标为已读 | `read_at = NULL`，删掉对应已读回写队列行           |
| 标为未读 | `read_at = now`，GitHub 来源重新入队               |
| 忽略     | 清空 `triaged_at / triage_outcome / triage_ref_id` |
| 转为待办 | 删除刚生成的待办 + 清空判断字段，细节见 5.2        |

撤销按 `appliedIds` 执行，不依赖筛选条件；单条失败不阻塞其余条目，返回失败 id 与原因。

### 4.6 边界状态

| 状态                     | 处理方式                                                         |
| ------------------------ | ---------------------------------------------------------------- |
| 未选中                   | 操作条不出现，`Esc` 直接退出                                     |
| 执行前条目被同步改动     | `WHERE triaged_at IS NULL` 兜底，影响 0 行计入 `skipped`，不报错 |
| 数量与确认时不一致       | `count_mismatch`，不执行，提示最新数量后重新确认                 |
| 部分失败                 | 成功项照常提交，结果报「2 条失败」，可只重试失败项               |
| 5 秒内又执行了另一个动作 | 新动作覆盖旧撤销记录，旧动作不可再撤销                           |
| 撤销超时                 | 「已忽略 / 已转待办」Tab 的单条撤销兜底                          |
| 邮件来源                 | 忽略只影响本地，不改变服务器，操作条旁写明                       |
| 批量标已读               | 写 N 条回写队列，限流见 4.8                                      |
| 离线 / 退避中            | 本地照常执行，回写排队重试                                       |

### 4.7 分阶段落地

- **Phase A（1–1.5 天）**：`ids` 选择 + 四个动作 + 5 秒撤销。单条与批量同路径，详情页按钮改为调用同一命令、成功后走同一个 callout。
- **Phase B（0.5–1 天）**：`filter` 选择 + 「选择全部 N 条」+ `expectedCount` 守卫。
- **Phase C**：规则化自动处理，形态见 5.4，在 v0.6 的最后一个阶段落地。

验证口径：Phase A 用 fixtures 造 60 条，走「全选当前页 → 忽略 → 撤销」与「转待办 → 撤销 → 二次转换不撞唯一索引」；Phase B 验证确认期间同步插入新消息时拒绝执行并重新确认。

### 4.8 风险

- **限流**：批量标已读会为每条消息写一条 GitHub 已读回写，当前 worker 一分钟一轮、逐条 PATCH。一次 100 条就是 100 次请求。建议批量场景只写本地，回写按批合并，或明确告知「稍后同步」。
- **撤销窗口很短**：5 秒只在「马上后悔」时有用，过期只能逐条救。所以大批量确认框必须写清数量与前几条标题。
- **语义漂移**：按钮写「移出待处理」，不写「清空」，否则用户会以为消息被删。
- **选择态与列表点击冲突**：列表行整行可点（切详情），复选框必须 `stopPropagation`，否则点选框会顺带切详情。

### 4.9 涉及模块与影响

- 后端：`commands/inbox.rs`（`apply_inbox_action` / `undo_inbox_action`）、`commands/dto.rs`（selection 解析与校验）、`application/inbox/mod.rs`（批量事务、撤销、待办删除或解关联）、`repositories/inbox_message.rs`（按 selection 解析 id、批量更新）、`domain/inbox.rs`（动作枚举与结果结构）。
- 前端：新增 `features/inbox/selection.ts`（选择状态与计数）、`features/inbox/BulkActionBar.tsx`、`features/inbox/UndoToast.tsx`；改 `InboxPage.tsx`、`InboxMessageDetail.tsx`、`lib/api.ts`、`fixtures.ts`。
- 影响：待处理积压有了出口，收件箱回到「今天的清单」；代价是 `InboxPage` 再涨 200 行左右，所以选择态与操作条必须外置。

## 5. 决策记录与三个追问

### 5.1 八条决策

| #   | 原问题           | 决定                                   |
| --- | ---------------- | -------------------------------------- |
| 1   | 「一键」的主语   | 抽象为「选择 + 动作」，不设固定语义    |
| 2   | 跨分页全选       | 做，「选择全部 N 条」                  |
| 3   | 撤销保留期       | 内存态，5 秒                           |
| 4   | 撤销「已转待办」 | 一律解绑保留待办，不删除，见 5.2       |
| 5   | 邮件侧写回       | v0.6 直接做 `\Seen`，不做 MOVE，见 5.3 |
| 6   | 批量转待办       | 做，作为普通动作，不设独立入口         |
| 7   | 键盘逐条流       | 不做                                   |
| 8   | 规则化自动处理   | v0.6 试行，只对新消息生效，见 5.4      |

### 5.2 追问一：撤销「已转待办」的问题在哪

转换时（`repositories/inbox_message.rs:258`）在一个事务里做两件事：

```sql
UPDATE inbox_messages
   SET triaged_at = now, triage_outcome = 'task', triage_ref_id = ?task_id
 WHERE id = ?1 AND triaged_at IS NULL;

INSERT INTO tasks (id, title, note, origin_kind = 'inbox', origin_id = ?message_id, ...);
```

消息与待办互相指向：`message.triage_ref_id → task.id`，`task.origin_id → message.id`。而 `0006_tasks.sql` 上有一条唯一索引：

```sql
CREATE UNIQUE INDEX tasks_inbox_origin_unique ON tasks(origin_id) WHERE origin_kind = 'inbox';
```

「只把消息放回待处理、待办留着」的做法会撞在这条索引上：

1. 撤销时清空 `triaged_at / triage_outcome / triage_ref_id`，消息回到待处理；
2. 待办还在，`origin_id` 仍指向这条消息；
3. 用户再次对同一条消息点「转为待办」；
4. `INSERT INTO tasks` 撞上 `tasks_inbox_origin_unique`，`SQLITE_CONSTRAINT` 被映射成 `conflict`；
5. 界面报错，而用户完全无法理解「同一件事为什么不能转第二次」。

所以「保留待办」的真正问题不是两个入口难看，而是**二次转换会直接失败**，并且失败信息对用户没有意义。

「连待办一起删」的问题是可能丢输入：如果 5 秒内用户在待办页改了标题或备注，删除就丢了。5 秒内几乎不可能，但不能假设。

实现只有一种：**解绑保留**。

- 撤销时清空消息的三个判断字段，同时 `UPDATE tasks SET origin_id = NULL WHERE id = ? AND origin_kind = 'inbox'`；
- 待办保留标题、备注与完成状态，`origin_kind` 仍是 `'inbox'`（列表里仍显示「来自收件箱」，只是没有「查看原消息」入口）；
- `origin_id` 置空后局部唯一索引不再拦路，用户可以再次转换；
- 若待办已被删除，跳过，不算失败。

唯一不允许出现的状态仍然是：消息回到待处理、待办仍占用 `origin_id`。删待办的方案被否掉的理由很直接——5 秒内用户在待办页加过一个字，删除就丢了。

### 5.3 追问二：邮件侧写回有多复杂

三件事的成本差一个数量级。

| 方案               | 实现                                                                     | 复杂度                      | 代价                                                                                                     |
| ------------------ | ------------------------------------------------------------------------ | --------------------------- | -------------------------------------------------------------------------------------------------------- |
| 本地忽略（现状）   | 只写 `triaged_at`                                                        | 无                          | 无。网页邮箱里邮件仍会存在——「忽略」是「别在收件箱提醒我」，不是「归档这封邮件」                         |
| 标记服务器 `\Seen` | `UID STORE +FLAGS (\Seen)`，复用现有已读回写队列                         | 低，约半天                  | 与「只读收信、不改变服务器已读状态」的承诺冲突，必须做成按账户开关并改文案；QQ / 163 对 STORE 有频率限制 |
| 移动到归档文件夹   | `LIST` 发现文件夹 → `UID MOVE`，或 `COPY` + `STORE \Deleted` + `EXPUNGE` | 中高，约 2–3 天，且长期维护 | 破坏只读承诺；`EXPUNGE` 不可逆；部分服务商不支持 `MOVE`；文件夹命名各异；移动后 UID 失效，游标要重建     |

判断（2026-11-27 修订）：

- **v0.6 做「标记 `\Seen`」**，不做 MOVE。单用户自用，不必在信任成本上保守；复用现有回写队列，按动作分派，按账户合并成一条 `UID STORE`。
- 承诺要跟着改：发布说明里「只读收信、不改变服务器已读状态」必须删掉，设置页文案改为「标为已读时会同步到邮箱」。
- 只做 `+FLAGS`，不做 `-FLAGS`：本地标未读不会把邮箱里的邮件翻回未读，这一点要在界面上说清。
- `UIDVALIDITY` 与入队时不一致则丢弃该行——宁可少标一封，不标错一封。
- **MOVE 不做。** `EXPUNGE` 一旦出错，代价是用户邮件被删。

### 5.4 追问三：规则化自动处理是什么

意思是：把「选择 + 动作」里的人工部分交给一条保存下来的规则，在消息入库时自动执行。

一条规则长这样：

```
当 来源 = GitHub 且 类型 = ci_failed 且 标题包含 "Dependabot"
则 忽略
```

落到数据上是一张表 `inbox_rules(id, source_id?, category?, actor_contains?, title_contains?, action, enabled, created_at)`；在 `application/inbox/ingest` 之后、广播事件之前匹配，命中就调用与 4.2 相同的动作实现，并记下 `triage_by = 'rule'`。

它解决的问题：每天 20 条 Dependabot 通知都要手动忽略，规则让这件事只发生一次。

代价与风险：

- 需要一次迁移（`inbox_rules` 表 + `triage_by` 列），含设置页与试跑约 2–3 天；
- 规则是静默生效的，写宽了会把该看的消息藏起来。缓解：只在入库时对新消息生效、不回溯；命中项在「全部」里带「规则」标记；每条规则支持「按最近 14 天试跑，命中 N 条」；
- 规则一多就变成一个小型邮件过滤器，维护成本会超过它省下的点击。

结论（2026-11-27 修订）：**v0.6 试行**，但按「先跑动作、再固化规则」的顺序放在最后一个阶段。规则的上限是两三条、只作用于新消息；如果试用后发现规则数量在增长，就说明动作集还不够抽象，该回去改动作，而不是继续加规则。

## 6. 验证方式

- 文案：`pnpm lint`、`pnpm build`、`pnpm check:design`、`pnpm format:check`；逐页走查 `?preview&view=inbox` 与设置页，确认无开发路径、无 `UIDVALIDITY`、无「判断」字样。

- 窄屏：820×900 下 4 个 Tab 是否换行、选择态操作条是否遮挡列表与详情。

## 7. 不建议做的事

- **不建议做 AI 分诊。** 个人工作站的消息量用规则就能覆盖，模型判断错的成本（漏掉 review 请求）远高于收益。
- **不建议把已读和已处理合并成一个状态。** 两者正交是合理的，「读完先放着」是真实需求；问题在展示方式，不在模型本身。
- **不建议新增「待处理」以外的状态枚举。** 现有 `triaged_at + outcome` 已经够表达，加 `status` 列只会重演 v0.4 之前 `items.status` 的老问题。
